# 一个教练，一个连续对话

2026-10-19。状态：用户已确认 UX 方向，尚未实现普通对话的 app 接入。
本文件是下一阶段功能范围，不代表现有 IPA 已具备这些能力。

## 用户已经确认的方向

- 普通对话是有价值的实际使用场景，应接入 openGym。
- app 只有一个“教练”入口、一个连续对话界面。
- 不显示 persona、agent、proposal、工具权限开关，不要求用户切换模型或运行模式。
- 不做“聊训练 / 计划建议”双标签；后台执行分工不映射成两个可见教练。
- 不添加仅为完成测试而存在的取消/撤回功能；此前 L2 的手机步骤仍不适用。

## 主要使用流程

1. 打开教练后直接聊训练：动作、恢复、近期记录、目标与安排。普通问题正常回答，
   不把每一条消息都当成计划复盘或修改指令。
2. 需要把讨论落实为计划时，在同一对话中使用“生成计划建议”。已有的新建计划、
   检查训练、调整计划等操作仍可作为快捷动作，不作为 persona 选择器。
3. 对话中展示本次要求的简短摘要，用户可修改，例如：
   “本周练两天，每次 45 分钟，尽量保留当前主要动作”。复用已有目标/器材资料；
   只有缺少生成计划所需信息时才补问，不让日常聊天先走完整问卷。
4. 生成期间显示同屏任务卡。完成后变成计划或调整建议卡，沿用现有预览、校验、
   应用/拒绝流程。单纯聊天不修改训练计划。
5. 点“应用到计划”后由 app 执行更改，对话显示结果。继续问“为什么这样安排”
   仍留在同一界面，且能明确讨论的是哪一份建议。

默认路由为普通对话。v1 通过明确的生成操作触发提案，不依赖关键词把普通消息
猜成计划修改。用户用自然语言要求生成时，教练应引导同屏操作，不让用户去设置里
切换 persona。路由细节始终由服务端处理。

## 连贯性与数据范围

用户需要知道的是“教练可以参考已同步训练”和“应用前计划不会改变”。
普通对话可使用只读 MCP 查询完整已同步历史，现有提案仍只使用其限定 payload；
两者的数据范围应在首次使用的说明中准确表述，不能沿用不准确的数据披露文案。

- 同一 app 对话的普通消息延续同一 conversation；提案请求仍使用独立 request/session。
- 交给提案通道的是用户确认的需求摘要，加上现有结构化训练 payload；
  不把完整对话、MCP 原始输出或 persona 记忆整包塞入提案。
- 提案卡保留用户要求、提案标识和状态。聊天讨论已有提案时带上明确的引用，
  不能把尚未应用的草稿当成已经执行的计划。
- 不自动导入用户在 OpenClaw 其他入口的聊天记录。普通对话 persona 的使用方式可以
  复用，但 app 会话与其他会话之间的对应关系需要显式定义。
- 生成中离开页面、回来、断线重连不能重复启动任务。消息失败提供针对该消息的重试。
  提案在后台生成时允许继续讨论；后续新要求不会悄悄改写已经提交的任务。
- 更换登录账号时按账号隔离对话与提案引用。未同步/数据不可达时如实说明，
  不能假称已读取训练数据。

## Mac / Linux 实施边界

| Mac | Linux |
| --- | --- |
| 统一教练界面、普通消息与提案卡的状态、中文及其他 locale 文案 | 给受限 bridge 增加普通对话通道，并更新 gym-coach 提示 |
| openGym 会话/消息 API、用户鉴权与绑定、客户端会话持久化方案 | 将普通对话稳定路由到 gym-coach，继续用 gym-coach-proposal 执行提案 |
| 从对话转为可编辑的生成要求、沿用提案校验和用户确认应用 | 按指定账号使用只读 MCP，保证会话隔离与真实数据读取 |
| API/客户端测试、实际 UI 验证、功能接通后的新版 IPA | 实际 OpenClaw 联调、并发/断线行为、部署与运行证据 |

当前 bridge 的 `/v1/chat/completions` 明确拒绝非 `proposal` 模式，因此此功能不能仅靠
在手机上切换 model 名实现。先明确新增会话协议，再按上述边界实施；不把原提案路由
直接改成有 MCP 权限的聊天路由。

普通对话通道至少需要以下合同，由 Mac 与 Linux 在实现前对齐：

- 请求绑定已认证的 profile、由服务端分配的 conversation ID 和独立 request ID；
  客户端不能指定任意 OpenClaw agent/session 或透传任意路由头。
- 每次发送都有可判定的完成/失败状态；重试同一 request ID 不重复生成或追加消息。
- 输出为可展示的 assistant 正文；工具执行及思考内容不能被误作最终回复。
  消息长度、耗时、历史保留量有界，错误信息不暴露内部凭证。
- 通过能力声明确认 bridge 已支持普通对话，再向该账号启用新体验；旧部署保持现有
  提案功能并给出准确提示，不能静默把“聊天”送到提案接口。

以上是功能范围，端点命名和传输方式在两端协议中确定。其验收是用户正常聊天、
MCP 读到真实同步数据、同屏生成/预览/应用、后续讨论能指向正确提案，以及两个执行
通道继续遵守各自数据范围。没有额外 persona 切换验收。
